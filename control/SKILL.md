# Control

把复杂编码任务拆成**技术方案 / 代码框架 / 项目代码**三层产物，固定一条**单向推导链**，并强制分三种模式分阶段推进。**每次启动或继续任务都必须先确定当前模式，再加载该模式对应的 Reference 行为文件，最后才执行**——不要在未确定模式、未加载对应 Reference 的情况下直接动手。上下文足够明确时直接判定模式并继续，不向用户发问；只有无法明确判定时才询问。

## 输出约定

control 任务激活后，**每一条回复都必须先在第一行输出当前模式**，格式固定为：

```text
当前模式为: <技术方案 | 代码方案 | 落实代码 | 待确认>
```

- 这一行先于任何正文、分析、代码或工具结果说明，每条回复都不能省略。
- 该占位符只能取上述四种值之一；尚未确认模式时输出 `当前模式为: 待确认`，并立即走启动确认门。
- 模式中途切换后，从切换那条回复起按新模式输出。

## 核心原则

```text
design/*.md（产品意图 + 技术方案） ──推导──▶ code/（可编译代码框架） ──推导──▶ 项目代码
```

- `design/*.md`：整个任务的最高事实依据，每篇同时承载两部分内容——**产品意图**（用户可见行为与交互：进入页面看到什么、何时触发、列表怎么变、边界怎么表现）与对齐它的**技术方案**（模型职责与事实源、管线流程、状态机、生命周期、数据流）。文档内**产品意图的确定性高于技术方案**：两者冲突时修技术方案，不为实现便利反写产品意图。技术方案只讲**技术上怎么运转**，不落到文件/属性/方法级代码抽象。
- `code/`：在 design 基础上推导出的**可编译 Swift 伪代码包**——`Sources/` 下按**真实组件拆分模块目录**（如 `Sources/XPhotos` 主工程、`Sources/XPhotoKits` 自定义相册 SPM 库），模块内按 **best-ios 分层**；用关键类型、方法签名与中文注释表达整体代码设计、类型职责、引用关系和 Event-Command 流程；**只表达总体设计与业务流程，日志、埋点、上报等横切实现细节不建模**。**类和函数的定义即最终态**，落实阶段直接照搬。
- 项目代码：严格按 `code/` 框架还原的实现，结构与内容和框架完全一致，框架没有的代码删除（日志等横切细节豁免——框架有意不建模，既有日志保留）。

### 事实依据优先级

**上游产物的确定性永远高于下游产物**：`design/*.md` > `code/`（代码框架） > 项目代码；design 文档内部，产品意图 > 技术方案。

- 越上游越接近“唯一事实源”：design 的确定性高于 code，code 高于代码。
- 三者冲突时一律以上游为准：下游必须服从上游，而不是上游迁就下游。
- 上游只在自身被证明有明确问题时才修改，且修改后必须重新向下游逐层传导。

### 推导只能从上游流向下游

- 由 `design/*.md` 推导 `code/` 框架，由 `code/` 框架推导代码；不允许反向。
- **不因为技术实现的需要去改产品意图**——除非产品意图自身有明确问题（目标自相矛盾、范围有漏洞、与客观事实不符），且经用户确认。
- **不因为 `code/` 框架的需要去改 `design/*.md`**——除非技术方案自身有明确问题（流程逻辑错误、事实源自相矛盾、根本无法实现）。
- **不因为现有代码的问题去改 `code/` 框架**——除非框架自身有明确问题（引用了不存在的能力、分层错误、根本无法实现）。
- 下游与上游不一致时，**默认修下游使其符合上游**；只有当某一层被证明有明确问题时，才回到那一层修正，并把修正继续向下游传导（改了 design 就重推 code→代码，改了 code 就重落代码）。

## 任务目录

每次开启新的 control 任务，先在 `elaboration/` 下创建一个总功能点文件夹；两层产物分别落在 `design/`、`code/` 子目录下，账本与目录固定在根目录：

```text
elaboration/<meaningful-task-slug>/
├── README.md          # 两层总目录（阅读顺序 + 各产物一句话说明）
├── change.md          # 变更账本（只含待落地），见 reference/change-log.md
├── archive.md         # 已归档变更（change.md 条目落实后移入），见 reference/change-log.md
├── question.md        # 方案审查清单（A 矛盾 / B 决策 / C 风险），见 reference/question-list.md
├── design/            # 技术方案（含产品意图）：按技术关注点命名
│   ├── models.md
│   ├── <concern>.md
│   └── ...
└── code/              # 代码方案：可编译 Swift 伪代码包（模块目录镜像真实组件拆分，模块内按 best-ios 层）
    ├── Package.swift  # Foundation 级依赖的独立 SPM 包（每个模块一个 target，按真实依赖方向连 target 依赖），始终保持 swift build 通过
    ├── .gitignore
    ├── AGENTS.md      # 包定位、模块与目录职责、代码与注释约束、方案对齐规则
    └── Sources/
        ├── XPhotos/       # 例：主工程模块（真实组件叫什么，模块目录就叫什么）
        │   ├── Model/     # Entities / Items / Nodes / Values
        │   ├── Utils/
        │   ├── Services/
        │   ├── Manager/
        │   ├── Store/     # Event / Command / Store
        │   ├── Controller/
        │   ├── View/
        │   ├── Entry/
        │   └── Support/   # 包内最小通用协议与占位工具
        └── XPhotoKits/    # 例：自定义相册 SPM 库模块，只建涉及的层
```

- 总功能点文件夹名只用有意义的英文任务名（kebab-case，如 `duplicate`、`dedupe-pause-resume`），不加日期或时间戳；命名反映任务内容而非时间。
- 一个总功能点内可以有多个 design 文档；不要为同一个大功能拆多个 `elaboration/` 顶层任务文件夹。
- 如果用户明确要继续已有任务，先读取该文件夹下相关 `design/*.md` 与 `code/` 框架源码；无法判断具体范围时，先读 `README.md` 并列出目录，必要时询问用户。
- 旧任务如果仍是 `product/` + `design/` + `code/` 三层旧结构，或 `plan/` + `coding/` 两层旧结构，可按旧结构继续读取（旧 `product/*.md` 视作该任务 design 层产品意图的历史载体）；除非用户要求迁移（如把 product 合并进 design），不主动改目录结构。
- 如果上下文没有任务名，根据需求语义生成一个简洁且可辨识的英文 slug；如果无法判断是在新建还是继续，先询问用户。
- `design/*.md` 可以先创建并持续更新；`code/` 包只有在进入代码方案模式后才创建并写入实质内容，项目代码只有在落实代码模式才动。
- 根目录四个账本文件（`README.md` / `change.md` / `archive.md` / `question.md`）**任务一开始就创建空壳**，不等到第一次有内容才补建。

### 分层组织与命名规则

两层的组织维度不同，**不强制文件名一一对应**；推导链靠**内容回溯 + 交叉链接**维系，不靠文件名匹配：

| 层 | 组织维度 | 命名 | 例 |
| --- | --- | --- | --- |
| design | 按**技术关注点**（每篇内先产品意图、后技术方案） | 有意义的英文 kebab-case | `models` / `scan-pipeline` / `scan-lifecycle` / `home` / `detail` |
| code | 先按**真实组件**建 `Sources/<模块>/`，模块内按 **best-ios 层**建目录（只建相关层） | 模块目录用真实组件名，层目录用层名 | `Sources/XPhotos/Model` / `Sources/XPhotoKits/Services` |

- 一个技术关注点可能承载多个产品能力，一个产品能力也可能横跨多个关注点文档；同一事实只在最合适的一篇里写一次，其它篇用相对链接引用。
- code 层**先按真实组件拆模块、模块内固定按 best-ios 层建目录**（不按功能拆）：真实项目代码分布在哪些组件（主工程、自定义 SPM 库等），`Sources/` 下就建哪些同名模块目录（如 `XPhotos` / `XPhotoKits`），用文件夹表达组件拆分；模块内同一功能的模型落 `Model/`、状态调度落 `Store/`、编排落 `Manager/`，一个层目录 = 一个 best-ios 层的代码骨架。只建当前任务真正涉及的模块与层目录，另有 `Support/` 放包内最小通用协议与占位工具。
- **跨层回溯靠交叉链接**：code 层的设计依据登记在 `README.md` 的 code 表（各层目录 / 关键源文件对应哪些 design 文档），Swift 源码内不写 markdown 链接；文档内引用其它文档用相对链接（如 `[design/models](../design/models.md)`）。
- **孤立无上游依据的下游内容按偏移处理**：若某技术方案条目回溯不到任何产品意图、或某 code 框架内容回溯不到任何 design 方案，默认删除该下游内容；只有确属上游漏掉必要目标时才回上游补齐。
- 继续已有任务或进入下游模式前，先读 `README.md` 校验两层覆盖关系；除尚未进入对应模式的层外，每个下游产物都应能回溯到上游依据。

## 四个账本文件

任务根目录固定有四个跨全任务共用的账本文件，机制细则各自独立成篇，**用到时才加载对应 Reference**：

| 文件 | 作用 | 机制文件 |
| --- | --- | --- |
| `README.md` | 两层总目录：列出 design 各文档与 code 各层落点的一句话说明、建议阅读顺序 | 无（结构见任务目录示例；每次增删文档或 code 层目录时同步更新） |
| `change.md` | 变更账本：只含 `## 待落地`（方案已改、代码未落），**日常只读这个文件**，跨模式协作 | `reference/change-log.md` |
| `archive.md` | 已归档变更：只含 `## 已归档`，change.md 条目落实后整条移入；仅追溯历史时读取 | `reference/change-log.md` |
| `question.md` | 方案审查清单：通读两层后仍待确定项（A 矛盾/漏洞、B 待拍板决策、C 风险确认），定案落文档后移除 | `reference/question-list.md` |

- **README.md**：两层结构的入口索引，仿 [elaboration/duplicate/README.md](../../../elaboration/duplicate/README.md)——顶部写两层关系与阅读顺序，再用两张表分列 design 各文档链接与一句话内容、code 各层目录（或关键源文件）与其设计依据。任务一开始建空壳，每次增删文档或 code 层目录同步维护。
- **change.md / archive.md** 与 **question.md** 的写入 / 落实 / 归档 / 定案生命周期细则不写在本文，分别见 `reference/change-log.md`、`reference/question-list.md`；进入相关模式时按需加载。

## 三种模式

control 任务固定分三种模式，每种模式的详细行为放在独立 Reference 文件，**确认模式后只加载当前模式那一份**：

| 模式 | 单一聚焦（本模式只做这件事） | 必要产物 | Reference 行为文件 |
| --- | --- | --- | --- |
| 技术方案 | 只制定 / 收敛 `design/*.md`——先明确产品意图（用户可见行为、交互、边界、验收标准），再产出对齐它的技术方案（模型/管线/状态机/数据流），不写代码框架和代码 | `design/*.md` | `reference/design-scheme.md` |
| 代码方案 | 只把 design 转成对齐它的可编译代码框架（`code/` Swift 伪代码包，类和函数定义即最终态），不写生产实现 | `design/*.md`, `code/` 框架 | `reference/code-scheme.md` |
| 落实代码 | 只按 `code/` 框架完成代码还原，项目代码与框架结构内容完全一致，不重新设计方案 | `code/` 框架, 项目代码 | `reference/implement-code.md` |

**单一聚焦原则**：每种模式只对自己那一层产物负责，向上以上游为准、不反向改上游，向下不替下游越权。

- 技术方案：既关注产品意图（用户价值、流程闭环、交互与边界，写成用户视角的可验证行为），也关注技术如何实现它（模型职责、事实源、管线、状态机、数据流）；可以出现模型/实体/类型的代码名称帮助理解，但不落到逐属性/逐方法的代码框架。
- 代码方案：只关注把 design 落成可编译代码框架（按真实组件拆模块、模块内 best-ios 分层；类和函数定义即最终态），**对齐 design 即可**；不扩大需求、不写生产级实现、不动项目代码。
- 落实代码：只关注把项目代码还原到与 code 框架结构内容完全一致（定义照搬、函数体按步骤注释补生产实现、框架没有的代码删除）；不重新做方案设计，发现上游问题先回到对应上游模式而非就地改代码逻辑。

触发线索：
- 用户在讨论**用户价值 / 交互 / 产品行为 / 验收标准**、要“技术方案 / 怎么实现 / 模型怎么设计 / 管线 / 状态机 / 写 design”，或刚开始复杂任务 → 技术方案。
- 用户要“代码方案 / 伪代码 / 代码框架 / 分层怎么写 / 类和函数怎么设计” 且 design 已有明确技术方案 → 代码方案。
- 用户要“开始写代码 / 按 code 落实 / 实现” 且 code 框架已可编译 → 落实代码。

### 启动确认门（每次启动/继续任务必走）

1. 读取或创建当前总功能点目录，读 `README.md` 校验 design / code 两层覆盖与回溯关系，定位相关文档现状。
2. 根据用户最新请求和产物状态推断当前应处于哪种模式，并识别这次是**产出**意图（制定/编写产物）还是**检查**意图（审查产物合理性）。
3. **确定模式**：上下文足够确定模式时，直接在模式行声明判定结果并简述判定依据（模式、产出还是检查、涉及哪些文档、将加载的 Reference 文件），不向用户发问、直接继续；只有无法明确判定时，才让用户在三种模式中选择（只问这一个问题）。
4. 用户确认后，加载该模式对应的 `reference/*.md`，再严格按其执行步骤、写作要求与汇报要求行事；检查意图按下文「检查（合理性审查）」执行。
5. 任务中途需要切换模式（如从技术方案转入代码方案）时，重新走一遍启动确认门并加载新的 Reference 文件。
6. 同一模式连续推进时不必每条回复都重新征求确认，只需保持输出模式行；只有启动、继续或切换模式时才走本确认门。

## 检查（合理性审查）

当用户的意图是**检查/审查/校验合理性**（而非产出新内容）时，按当前模式审查对应层级产物，**检查范围随模式不同**，越下游的模式检查的层级越多：

| 模式 | 检查范围 |
| --- | --- |
| 技术方案 | 只查 `design` 自身合理性：产品意图自洽（目标、范围完整、数值明确、用户流程闭环、与客观事实不冲突）+ 技术方案对齐产品意图 + 内部自洽（事实源唯一、状态流转无死角、跨文档引用不矛盾），不查代码框架与项目代码 |
| 代码方案 | 查 `code` 框架与 `design` 是否冲突（顺带回溯技术方案与产品意图一层），不查项目代码 |
| 落实代码 | 查 `design`、`code` 框架、项目代码三者是否冲突 |

### 标记规则

- **明显冲突 → 标记为「错误」**：下游与上游存在矛盾、违背或超出（如技术方案做了产品意图没要求的事、code 偏离 design、代码偏离 code、下游流程与上游相悖）。
- **上游缺失 → 标记为「警告」**：下游需要的依据在上游里没有（如产品意图缺目标/数值、产品意图有要求但技术方案未覆盖、design 有方案但 code 未覆盖、code 缺代码所需方案）。
- 输出固定用前缀标注，便于扫读：

```text
- [错误] <冲突点>：下游 <…> 与上游 <…> 冲突
- [警告] <缺失点>：上游 <…> 缺少下游需要的 <…>
```

- 检查只负责**报出**错误与警告并给出应走的处置建议（修下游 / 回上游补齐，对应「偏移处理」）；真正的修正在用户确认后回到对应产出模式执行，**不在检查回合里静默改产物或代码**。

## 偏移处理

一切偏移都遵循同一条铁律：**默认修下游使其符合上游，上游仅在自身被证明有明确问题时才动。**

- **需求偏移**：技术方案、code 框架或代码要做的事超出 design 里的产品意图。默认删掉这部分下游内容；只有当确属产品意图自身有明确缺口时，才停止实现、先更新 design 的产品意图并让用户确认，再逐层向下传导。
- **方案偏移**：code 框架或代码结构与 design 技术方案不一致但不改变产品意图。默认修下游去贴合 design；只有当技术方案自身被证明有明确问题时，才回到技术方案模式更新 design 再继续——不因现有代码框架或代码的写法反推改 design。
- **框架偏移**：代码结构与 code 框架不一致但不改变技术方案。默认修代码去贴合 code；只有当 code 框架自身被证明有明确问题时，才回到代码方案模式更新框架再继续。
- **实现偏移**：代码没有按 code 框架落实（定义与框架不一致，或存在框架没有的多余代码），修正代码——定义照框架还原、多余代码删除（日志 / 埋点 / 上报等横切细节豁免，不算多余代码）；不要用改框架掩盖实现偏差。
- **验证偏移**：验证方式和 design 产品意图的成功标准不一致，先补齐验证说明，再决定是否补测试或运行命令。
