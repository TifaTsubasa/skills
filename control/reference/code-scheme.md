# 代码方案模式

> 仅在启动确认门确认为「代码方案」模式后加载本文件。

**单一聚焦：本模式只产出对齐 design 的可编译代码框架（`code/` 下的 Swift 伪代码包，按真实组件拆模块、模块内按 best-ios 分层）。** 唯一目标是把技术方案翻译成可编译、可审查、可回溯的**代码骨架**——用关键类型、方法签名和中文注释表达整体代码设计、类型职责、引用关系与 Event-Command 流程，对齐 design 即可，不扩大需求、不写生产级实现、不改项目代码。框架里**类和函数的定义都是最终态**：类型名、属性、方法签名、参数与访问控制在本模式定稿，落实代码阶段直接照搬引用、不再二次设计；占位的只是函数体，不是定义。design 的确定性高于 code：框架里每个类型、方法、流程都必须能回溯到 design，回溯不到的默认删除，不反向改 design。

## code 层形态（可编译 Swift 伪代码包）

`code/` 是一个独立 SPM 包而非 markdown 文档，靠「能编译」保证类型关系、引用关系与命名真实成立：

```text
code/
├── Package.swift        # Foundation 级依赖的独立包（macOS 平台即可；每个模块一个 target，按真实依赖方向连 target 依赖）
├── .gitignore           # 忽略 .build 等构建产物
├── AGENTS.md            # 包定位、模块与目录职责、代码与注释约束、方案对齐规则
└── Sources/
    ├── XPhotos/         # 例：主工程模块；模块内按 best-ios 层建目录，只建当前任务涉及的层
    │   ├── Model/ …     # 见下方分层表
    │   └── Support/ …
    └── XPhotoKits/      # 例：自定义相册 SPM 库模块
        └── Services/ …
```

- **模块目录镜像真实组件拆分**：真实项目代码可能分布在不同模块（主工程、自定义 SPM 库等），`Sources/` 下为每个涉及的真实组件建同名模块目录（如 `Sources/XPhotos` 主工程、`Sources/XPhotoKits` 自定义相册 SPM 库），用文件夹表达组件拆分；`Package.swift` 为每个模块声明一个 target 并按真实依赖方向连 `dependencies`，跨模块引用的类型必须 `public`，靠编译器保证组件边界与访问控制真实成立。
- **表达手段**：类型声明 + 方法签名 + 最小占位实现，配 `///` 一行中文注释与函数体内 `// 1. 真实实现…` 编号步骤注释；详细实现用注释描述，不写完整算法。
- **可编译是硬性门槛**：每次改动后 `swift build` 必须通过；编译器兜底保证「引用了不存在的能力、类型对不上、事件流断链」这类方案错误无处藏身。
- **它是设计产物不是生产实现**：不追求完整算法、真实数据库、系统框架（PhotoKit / UIKit / SwiftUI）细节或线上级错误处理；不为本包写测试。

## best-ios 分层（Sources 目录骨架）

每个模块目录 `Sources/<模块>/` 内按 best-ios 层建目录，不按功能拆；同一功能的逻辑按层散落（模型落 `Model/`、状态调度落 `Store/`、编排落 `Manager/`），一个层目录 = 一个 best-ios 层的代码骨架：

| 层目录 | 职责 | 依赖边界 |
| --- | --- | --- |
| `Model/` | Entities（DB 镜像）/ Items（业务）/ Nodes（视图）/ Values（Value / State / Config）四类文件，表达数据边界与页面状态；逐属性 `///` 注释 | 只依赖 Util，不依赖 Service / Manager |
| `Utils/` | 纯规则工具骨架（切窗、匹配、排序、选优、阈值判定），只表达输入输出与核心规则步骤 | 无业务依赖，可被各层复用 |
| `Services/` | 服务协议 + 空实现占位（数据库扩展、资产枚举、扫描 / 计算引擎），表达 I/O 与系统能力边界 | 依赖 Model / Util；不产视图 Node |
| `Manager/` | 业务编排骨架（常为 actor）：任务准备、管线推进、对账、闸门检查点；批处理 / 匹配 / 写库细节用步骤注释替代 | 依赖 Service / Util；对上经主动事件流（AsyncStream）回流 |
| `Store/` | Event / Command / Store 三类文件：`handle(event:)` 唯一入口、更新页面状态、输出 Command 批次 | 可依赖 Util，**不依赖 Service / Manager** |
| `Controller/` | 消费 Store 命令、调用 Manager，把 Manager 结果与主动事件转 Event 回流给 Store | 依赖 Store / Manager |
| `View/` | 可编译的渲染占位 + UI 事件上报闭包（ViewController / View / Cell 骨架） | 依赖 Store（订阅 Node）/ Model |
| `Entry/` | 入口装配、生命周期转发、present / dismiss 回写闭环 | 依赖 Controller / Store / View |
| `Support/` | 本包所需的最小通用协议或占位工具（仅限表达 UI / I/O 边界所需，不含日志等横切细节） | 无业务依赖 |

- 阅读与书写顺序**自底向上按依赖**：先被依赖的模块、后依赖方模块；模块内 Model → Utils → Services → Manager → Store → Controller → View → Entry。端到端链路从目录顺序里就能读出来。
- 用不到的模块 / 层不建空目录（如无自定义转场就不建 `Entry/`）。

## 包初始化流程（首次进入本模式时执行）

用 Swift Package Manager 命令创建伪代码包，再裁剪成纯 Sources 骨架：

```bash
mkdir -p elaboration/<task-slug>/code
cd elaboration/<task-slug>/code
swift package init --type library --name <主模块名>   # 生成 Package.swift / .gitignore / Sources / Tests
rm -rf Tests                                           # 伪代码包不写测试，删除 Tests 目录
```

初始化后手工收尾：

1. 精简 `Package.swift`：删除 `testTarget`；补 `platforms: [.macOS(.v13)]` 与 `swiftLanguageModes: [.v6]`；不添加任何外部依赖。按真实组件为每个模块声明一个 target（如 `XPhotos` / `XPhotoKits`），target 间按真实依赖方向声明 `dependencies`。
2. 删除模板生成的占位源文件，按真实组件在 `Sources/` 下建模块目录，再按 best-ios 分层表在各模块目录下建层子目录。
3. 补充 `AGENTS.md`：按下方「代码与注释约束」写清包定位（可编译伪代码、非生产实现）、各目录职责、代码约束、注释格式与方案对齐规则（对齐哪些 design 文档）；后续任何会话续写本包前都必须先读它。
4. 跑一次 `swift build` 确认空骨架可编译。

## 执行步骤

1. 先读取对应 `design/*.md`，确认技术方案（模型职责、事实源、管线、状态机、数据流）足够明确；不足则回技术方案模式补齐，不凭空写框架。
2. 定位或初始化 code 包：无包时按上方「包初始化流程」用 SPM 命令创建并裁剪骨架、补 `AGENTS.md`；已有包时先读 `AGENTS.md` 与现有源码再续写。
3. 在 `README.md` 的 code 表登记各模块 / 层目录（或关键源文件）与其设计依据（对应 design 文档链接）——Swift 源码内不写 markdown 链接，code 层的跨层回溯靠 README 维系。
4. 先按真实组件确定每个类型的模块归属，再按依赖自底向上写各层骨架，遵循「代码与注释约束」；**类和函数的定义写成最终态**——类型名、属性、方法签名、参数与访问控制即最终项目代码的定稿，落实阶段直接照搬；Event-Command 流程、持有关系、回流链路必须在代码里真实连通。
5. 每次改动后运行 `swift build` 确认可编译；编译不过不算完成本模式产出。
6. **显式标注模板偏离**：某层落地偏离 best-ios 标准模板时（如结果链路跳过 Item、Entity 因持久化技术留主工程、Manager 单例改构造注入），在对应类型的 `///` 注释或 `AGENTS.md` 显式写明偏离与理由，不隐藏。
7. 检查框架里每个类型、方法、流程都能映射回对应 design。不能映射的**默认删除**；只有当确属 design 自身漏掉必要方案时，才回到技术方案模式补 design 并让用户确认，再据此补框架——绝不为了迁就 code 反向改写 design。
8. **本次框架有变动时，把变动摘要写入 `change.md` 的 `## 待落地`**（见 `reference/change-log.md`）：注明变动主题、涉及的落点（`Sources/<模块>/<层>/<文件>.swift` 的类型 / 方法）与「待落实」状态；框架目标与项目现状代码的差异也记在对应条目里（Swift 源码内不承载差异表）。同一条未落实变动反复调整时更新同一条目，不重复追加；不在本模式落实项目代码，也不动 `archive.md`。

## 代码与注释约束（写进 AGENTS.md 并逐条遵守）

代码约束：

- **只表达总体设计与业务流程**：框架描述整体代码设计、类型职责、引用关系和 Event-Command 流程即可；日志、埋点、上报等**横切实现细节不建模**——不镜像既有基础组件（如 Log 包）、不新增契约协议 / 上报器 / logger 占位类型或调用，需要提示「真实实现会记日志」时只写一行编号注释。此类细节由真实工程既有设施承担，落实阶段也不因框架没有而删除项目代码中的既有日志。
- **定义即最终态**：类型声明、属性、枚举 case、初始化器与方法签名按最终项目代码书写（含参数标签、类型与跨模块 `public` 访问控制），落实代码阶段直接照搬，不出现临时命名或待定签名；占位的只有函数体。
- **模块归属即最终归属**：类型放在哪个 `Sources/<模块>/` 目录，落实时就落到真实工程的哪个组件；跨模块引用方向与真实组件依赖一致。
- 依赖保持 `Foundation` 级；不引入真实 App、数据库、照片库、UI 框架或日志框架依赖（UI / I/O 用最小占位协议与占位类型表达边界）。
- 以「类型声明 + 方法签名 + 最小占位返回」为主，避免把 production 细节补完整；占位返回用明显默认值（`[]`、`[:]`、`nil`、`false`、`0`、空字符串、空节点）。
- 函数需要表达真实流程时，用编号注释替代详细实现（`// 1. 真实实现…`、`// 2. …`），按执行顺序递增；编号注释描述真实实现会做什么，不写抽象说明；需要保留调用关系时保留真实调用（如 `// 1. 这里只保留 Node -> Util 的调用关系…`）。
- 除空实现占位外，不新增只有一行实现的函数；至少用一行中文注释说明真实实现职责。
- 不做防御性编程，不为伪代码补方案未确认的 fallback、重试、兼容层或配置开关。

注释格式：

- 每个 `class` / `struct` / `enum` / `actor` / `protocol` 都用一行 `///` 中文注释说明作用。
- 每个模型属性、枚举 case、初始化方法、公开方法、私有辅助方法都用一行 `///` 中文注释说明作用；属性注释写清业务含义或稳定身份（如“系统资产标识”“组排序键”“以 assetId 作为稳定身份”）。
- 注释保持简明，不写大段背景说明；需要背景的沉淀回对应 design 文档。

## 检查（合理性审查）

检查意图下，审查 `code/` 框架与对应 `design/*.md` 是否冲突（顺带回溯技术方案与产品意图一层），**不审查项目代码**：

- 先跑 `swift build` 确认可编译；编译不过直接报 `[错误]`。
- 逐层核对框架的类型、属性、方法签名、编号步骤注释、Event-Command 流程能否回溯到 design 的模型职责 / 事实源 / 管线 / 状态流转。
- 核对模块与分层是否正确：类型落在对的模块目录与层目录、依赖边界不被违反（如 Store 引用 Service / Manager 即越界、模块依赖方向与真实组件相反）、层目录齐备且不混层。
- 核对约束是否被遵守：定义是最终态（无临时命名 / 待定签名）、`///` 注释齐备、占位实现未膨胀成生产实现、未建模日志等横切实现细节、模板偏离已显式标注、`README.md` code 表与实际目录一致。

标记：

- code 框架做了 design 没要求或与 design 相悖的事、编译不过、分层错误 / 依赖越界、未标注的模板偏离 → `[错误]`。
- design 有明确方案但框架未覆盖，或 design 缺少框架所需依据 → `[警告]`。

## 汇报要求

说明本次框架覆盖的模块与 best-ios 层、关键类型 / 方法与流程链路、`swift build` 结果、仍未覆盖的 design 项，以及移交 `change.md` / `question.md` 的变动与待确认项。
