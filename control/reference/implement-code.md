# 落实代码模式

> 仅在启动确认门确认为「落实代码」模式后加载本文件。

**单一聚焦：本模式只按 `code/` 可编译代码框架完成代码还原。** 不重新做方案设计、不扩展框架没表达的功能。还原的硬性标准是**项目代码与 code 框架的结构与内容保持完全一致**：框架里类和函数的定义都是最终态，类型、属性、方法签名照框架原样还原（框架的 `Sources/<模块>/` 归属对应真实工程组件），函数体按框架的编号步骤注释补成生产实现；**框架里没有的代码就是不必要的代码，一律删除**。code 的确定性高于代码，**落实时以 code 框架为唯一依据，不需要迁就、保留或兼容当前代码的既有实现**：凡是与框架不符的现有代码，默认**删除或改写**使其符合框架，不让旧实现牵制方案落地；只有框架自身被证明有明确问题时，才回到上游模式（代码方案，必要时再到技术方案）修正，而不是就地改代码逻辑绕过方案。

目标是让项目代码严格落实 `code/` 框架，并在实现过程中保持 design / code / 最终代码三层一致。

## 执行步骤

1. 读 `README.md` 校验两层覆盖，再按模块 / 层目录读取 code 框架中当前功能相关的源文件（`Sources/<模块>/<层>/`，模块目录对应真实工程组件）与其上游 design 依据；列出即将修改的项目文件及其对应的框架源文件与类型 / 方法。
2. **以 `change.md` 的 `## 待落地` 条目和「框架 vs 项目代码」对照为改码清单**：框架的类型 / 属性 / 方法签名是**最终态定义，照搬即可、不再二次设计**，函数体内 `// 1. 真实实现…` 编号步骤注释是方法体的实现说明，逐项对照现状代码差异，按目标改码。
3. 检查当前项目规则、相关文件头部 `Rules` 注释，以及任务触发的其他 skill（如 best-ios 分层、swift 并发、i18n 等）。
4. 按对应框架源文件还原代码，遵循框架的模块归属（类型落到 `Sources/<模块>/` 对应的真实工程组件）与 best-ios 分层：Model / Util / Service / Manager / Store / Controller / View / Entry 各归其位；不要实现框架没有表达的额外功能。框架里的占位实现（空返回、占位协议）在项目代码中替换为生产实现，但类型、属性、方法签名与流程和框架**完全一致**。
5. 落实过程中**不需要考虑当前代码的既有实现**，一律以框架为准：发现现有代码与框架不一致时，**默认删除或改写这部分代码使其符合框架**；框架中不存在的类型 / 属性 / 方法 / 分支就是不必要的代码，**一律删除**，不保留「以防万一」的旧逻辑，不要为了迁就、保留或兼容现有代码反向改写框架。**唯一豁免：日志、埋点、上报等横切实现细节**——框架按约束有意不建模（见 `reference/code-scheme.md`），项目代码中的既有日志 / 上报调用不属于「框架没有的多余代码」，落实时保留并按项目规范补齐，不据框架删除。只有当框架自身被证明有明确问题（逻辑错误、引用不存在的能力、分层错误、根本无法实现）时，才回到代码方案模式校正框架；若问题根源在 design（技术方案或产品意图），再回到技术方案模式更新并让用户确认。
6. 代码完成后反向核对：项目代码与框架结构内容完全一致——每个代码改动都能映射到框架的类型 / 方法，框架的每个类型 / 方法与编号步骤注释都已落实或明确延期，涉及范围内不存在框架没有的多余类型 / 属性 / 方法，design 产品意图的每个成功标准都有验证或说明。
7. 按项目要求运行最小相关验证；涉及测试编写或测试运行时，使用项目内测试 skill。

## 编码完成 change（change.md 驱动）

当用户要求「编码完成 change / 落实 change」时，以任务根目录 `change.md` 的 `## 待落地` 为落实清单，逐条闭环（机制细则见 `reference/change-log.md`）：

1. 读取 `change.md` 的 `## 待落地`，列出全部待落实条目；逐条处理（如用户指定某条则只处理该条）。
2. 按条目的「落点」读取 code 框架对应源文件（及必要的 design 依据）的具体方案——以框架为落实依据，change 条目只是索引，不替代框架。
3. 按上面的执行步骤据框架落实代码，保持 design / code / 代码三层一致。
4. 该条对应代码完成并通过最小验证后，把该条目从 `change.md` 的 `## 待落地` **整条移入** `archive.md` 的 `## 已归档` 顶部，状态改「已完成」并标注 commit 或时间；未完成或验证未过不归档。
5. 处理完继续下一条，直到 `## 待落地` 清空或用户指定的条目落实完毕。

- change 条目与 code 框架冲突时以框架为准（change 只记录变动索引）；code 与 design、技术方案与产品意图冲突按「偏移处理」逐层回上游。

## 一致性校验格式

```markdown
## 一致性校验
- design: <对应 design 文档的产品意图（用户行为 / 成功标准）与技术方案条目>
- code: <对应框架源文件的类型 / 方法>
- 代码: <对应文件 / 类型 / 函数>
- status: 已落实 / 延期 / 需要确认
```

## 检查（合理性审查）

检查意图下，审查 `design`、`code` 框架、项目代码**三者**是否冲突：

- 代码是否与 code 框架结构内容完全一致（模块归属、分层、类型 / 属性 / 方法签名、流程、状态变化、Command / Event、持久化、UI 反馈；框架里的编号步骤注释是否都有对应实现；是否存在框架没有的多余代码未删除——日志 / 埋点 / 上报等横切细节豁免，不算多余代码）。
- code 框架是否仍对齐 design、design 内技术方案是否仍对齐产品意图（顺带逐层回溯，避免上游已变而下游未跟）。
- `README.md` / 交叉链接与代码落点是否一致，`change.md` 的待落地条目是否已随实现移入 `archive.md` 归档。

标记：
- 代码偏离 code 框架（含存在框架没有的多余代码未删除）、code 与 design 相悖、技术方案与产品意图相悖、三者流程矛盾、分层越界 → `[错误]`。
- 上游（design / code）缺少代码所需依据，或下游已实现但上游未记录 → `[警告]`。

## 汇报要求

说明代码改动、三层产物同步、验证命令与一致性校验结果，以及从 `change.md` 移入 `archive.md` 归档的条目。
