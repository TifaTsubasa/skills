# BDD 需求拆解

把产品需求翻译成**标准 Gherkin** 格式的 BDD，写到 `docs/bdd/<feature-slug>.md`。输出只有一个 Markdown 文件，里面就是 Gherkin，不要任何多余的外壳。

## 工作流程

### 1. 先对齐需求，再动笔

读完需求后，**不要立刻开写**。在对话里先做：

- 用 1-2 句话复述你理解的核心用户价值
- 列出你识别到的 2-5 个主要场景分支
- 提出 3-5 个澄清问题，针对有歧义或没说清楚的点

只有当用户确认或补充完毕，才进入写作。如果用户说"按你理解的来"，直接进入下一步。

### 2. 确定文件位置

- 根据需求主题生成英文短横线命名的 slug，例如"照片时间线整理" → `photo-timeline-arrange`
- 目标文件：`<项目根>/docs/bdd/<feature-slug>.md`
- 目录不存在就创建
- **始终追加模式**：
  - 文件不存在 → 新建
  - 文件已存在 → 在已有 Feature 里追加 Rule/Scenario，或在文件末尾开一个新的 Gherkin 块
  - **不要**修改已有内容，**不要**加日期追加注释

### 3. 文件内容就是 Gherkin

文件最小结构：

````markdown
# <功能名称>

```gherkin
# language: zh-CN

功能: <一句话功能名>
  作为 <角色>
  我想要 <能力>
  以便 <价值>

  背景:
    假设 <所有场景共享的前置>

  规则: <按业务规则分组，可选>

    场景: <场景名>
      假设 <前置>
      当 <动作>
      那么 <可观察结果>
      而且 <补充结果>

    场景大纲: <参数化>
      假设 <前置>
      当 用户输入 <输入>
      那么 系统显示 <预期>
      例子:
        | 输入 | 预期     |
        | 空   | 提示必填 |
        | 超长 | 截断显示 |
```
````

就是 **一个 h1 + 一个 Gherkin 代码块**。不要 `## 背景与价值`、`## 变更记录`、`## 未展开维度` 这些外壳。

关键约束：
- **中文关键字**（`功能/背景/规则/场景/场景大纲/假设/当/那么/而且/但是/例子`）
- 顶部声明 `# language: zh-CN`
- **一个场景只测一个行为**
- **Given-When-Then 顺序**：Given 是状态、When 是触发、Then 是可观察结果
- **Then 不写实现细节**（不要出现"调用 XXX 接口"、"写入 XXX 表"）
- 数据驱动用**场景大纲 + 例子**表格，不要复制多个 Scenario

### 4. 边界 case 的覆盖策略

**第一层：直接写成 Scenario。** 逐项过下表，凡是跟本需求**直接相关**的就写进 Gherkin：

| 维度 | 常见表现 |
|---|---|
| 空/缺失 | 输入为空、列表为空、未登录、未授权 |
| 极值 | 0 / 负数 / 最大值 / 超长字符串 / 超大列表 |
| 格式错误 | 类型不对、非法字符、编码异常 |
| 权限 | 未授权、权限被撤销、权限级别不足 |
| 网络/IO | 离线、超时、慢网、请求失败、部分失败 |
| 并发 | 多端同时操作、快速连点、操作未完成又触发 |
| 状态切换 | 操作中断（切后台、杀进程、锁屏）、恢复后状态 |
| 数据一致性 | 重复操作幂等、撤销/回滚、乐观锁冲突 |

**第二层：在对话里列出来问用户。** 写完第一层后，**在聊天中**向用户列出未展开的维度清单，例如：

> 以下维度我还没展开，要继续拆吗？
> - 国际化（多语言、时区、RTL）
> - 无障碍（VoiceOver、动态字体、高对比度）
> - 多设备适配（iPhone/iPad、横竖屏）
> - 性能边界（大数据量、低内存）
> - 合规（隐私、数据保留期）

**不要把这个清单写进 .md 文件**。也不要把你做的假设写进文件，直接在聊天里列出来让用户 review。

判断"明显 vs 细致"：
- **明显** = 普通用户日常使用会自然遇到
- **细致** = 需要特定设备、特定配置、特定压力场景才会触发

## 风格要点

- **具体 > 抽象**：不要"用户进行合法操作"，要"用户点击'保存'按钮"
- **可观察 > 内部状态**：不要"状态机进入 Active"，要"按钮变蓝并显示'已启用'"
- **主语一致**：一个 Feature 里保持"用户"或"系统"视角一致
- **中文标点** + 代码/标识符保持原样
- **不要编造需求里没有的规则**：不确定就在澄清问题里问，不要自作主张写进 Then

## 反面例子

❌ 太抽象：
```gherkin
场景: 正常保存
  假设 用户输入了合法数据
  当 用户提交
  那么 保存成功
```

✅ 具体可验证：
```gherkin
场景: 保存一张带标题的新相册
  假设 用户在"新建相册"页面
  而且 标题输入框填写了"2026 旅行"
  而且 已选中 3 张照片
  当 用户点击"保存"
  那么 相册列表出现名为"2026 旅行"的相册
  而且 该相册封面显示第一张被选中的照片
  而且 页面返回到相册列表
```

❌ 实现细节写进 Then：
```gherkin
那么 调用 POST /api/albums 接口
而且 albums 表插入一条记录
```

✅ 只写可观察结果：
```gherkin
那么 相册列表顶部出现新建的相册
而且 该相册在杀掉 App 重启后仍然存在
```

## 交付清单

完成后，你应当：

1. 在 `docs/bdd/<feature-slug>.md` 产出/追加 —— 文件就是 h1 + Gherkin
2. 在聊天里简短总结：写了几个 Scenario、覆盖了哪些边界类型
3. 在聊天里列出**未展开的维度**，问用户要不要继续拆
4. 在聊天里列出**你做的假设**，让用户 review

## 何时不用这个技能

- 用户只是聊需求、没有"写下来"的意图 → 别主动触发
- 用户在写代码、测试脚本、实现细节 → 这是 TDD/单元测试的领域
- 用户明确说"只要简短的场景列表" → 直接列 bullet，别硬套 Gherkin
